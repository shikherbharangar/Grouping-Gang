## Real-browser limitation

The installed Chromium is **154.0.8037.57 on Linux**. Launching it with unpacked-extension flags produced no extension worker. A browser-level DevTools `Extensions.loadUnpacked` request returned:

> Loading of unpacked extensions is disabled by the administrator.

The restriction was not changed or bypassed. Brave/macOS is not installed. **No real Brave behavior is recorded as passed**, and no simulated API result is presented as proof of browser grouping or session restoration. Additional browser downloads were also blocked by network policy; they are not a dependency of the shipped extension.

V1.1 re-ran the same load probe on 14 October 2026 and received the same administrator-policy rejection. No real Brave checks passed. The production artifacts are prepared for local installation. Release acceptance remains conditional on the following tests on a Brave installation that permits unpacked extensions.

## Popup width regression (14 October 2026)

The initial V1.1 UI checks opened the launcher in a viewport already set to 560 px. They missed a bootstrap defect: the popup stylesheet replaced its fixed body width with `100vw` below 559 px, without minimum widths on the document or launcher. The same rule was present in the compiled CSS; the manifest pointed to the correct popup HTML. In Chromium, opening the built page at a 40 px initial viewport reproduced a 40 px document/body/launcher, an 8 px result list, a zero-width search input, and horizontal overflow. The new regression failed against that build before the fix.

The popup stylesheet now explicitly anchors the document, body and launcher at 560 px with a 520 px minimum and border-box sizing. The document has a 600 px maximum width/height. Once a sufficiently wide host viewport exists, it can yield space to a document scrollbar. Search flex sizing, nonshrinking status/action controls, wrapping notices/footer and constrained setup selects prevent child overflow. Shared settings styles and application logic are unchanged.

`npm run test:browser` now runs **41 checks**, including six geometry scenarios in `scripts/popup-geometry-check.mjs`. They measure the built DOM in real Chromium with Chrome API doubles and visible scrollbars. The 40 px initial viewport now produces a 560 px document/launcher, approximately 440 px search and 528 px results list. Five rows take 340 px total height; ten long-title rows take 370 px with a vertically scrolling list, aligned 28 px number columns and readable title columns. At a 300 px viewport height, document scrolling keeps footer actions accessible with no horizontal overflow. Loading, empty, recovery-progress, error, Undo and onboarding shells are also measured. Both themes, long-title results, onboarding and the short-height case were visually inspected.

Measurements are saved to ignored `artifacts/popup-geometry.json`; screenshots include `popup-ten-slots-light.png`, `popup-ten-slots-dark.png`, `popup-geometry-light.png`, `popup-geometry-dark.png`, `popup-geometry-short.png`, `popup-geometry-setup.png`, `popup-geometry-loading.png` and `popup-geometry-empty.png`. These render the production HTML/CSS with test fixtures; they are **not screenshots of a native toolbar popup**. A normal browser page cannot negotiate its host viewport size, so the test explicitly resizes the page after checking bootstrap geometry.

Build, 141 Vitest tests, strict type checking, ESLint and formatting pass. The rebuilt extension's native load probe again returned **“Loading of unpacked extensions is disabled by the administrator.”** Native Chromium/Brave popup auto-sizing and macOS display scaling therefore remain outstanding. Before accepting this fix for release, load the rebuilt `dist` in unrestricted Brave, open through the toolbar from a fresh popup, verify the intended width in both themes, and repeat with all ten slots, long names, onboarding and a shorter/scaled display. No native-popup verification is claimed by the renderer checks.
